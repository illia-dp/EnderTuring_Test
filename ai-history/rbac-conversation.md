# RBAC: три роли, централизованные проверки и компактные тесты

## Что уже есть

Архитектура подходит для небольшой доработки: FastAPI dependencies отвечают за авторизацию, SQLModel — за модели, Alembic — за миграции. На фронтенде используются TanStack Router и Query, API-клиент генерируется из OpenAPI.

- **Авторизация:** JWT содержит `sub` и срок действия. `get_current_user` загружает пользователя из БД при каждом запросе — это позволяет применять смену роли сразу, без перевыпуска токена.
- **Пользователи:** вместо ролей сейчас `is_superuser`. Схемы регистрации и обновления своего профиля уже отделены от административных — хорошая основа для защиты от повышения привилегий.
- **API:** список, создание, изменение и удаление пользователей доступны superuser; собственный профиль — всем авторизованным. Items ограничены владельцем, superuser имеет полный доступ.
- **Роутинг:** `/admin` проверяет superuser, но при отказе перенаправляет на главную. Общий обработчик ошибок разлогинивает при `403`. Для RBAC оба поведения нужно исправить.
- **Настройки:** `/settings` содержит личный профиль и пароль. Глобальных настроек приложения нет.
- **Тесты:** найдено 58 backend-тестов, есть Playwright-сценарии авторизации, пользователей, Items и настроек. Backend использует настоящий PostgreSQL и общую session-scoped фикстуру; CI требует coverage ≥90%.

Тесты просмотрены, но не запускались: в текущем окружении не обнаружены `uv`, `bun` и установленные зависимости. Прохождение существующего набора пока не подтверждено.

## Роли и модель доступа

Следуем небольшому объёму [ТЗ](https://github.com/evios/Fullstack-Dev-Test-Task): пользователи, защищённая metrics-заглушка, собственный профиль.

- **admin:** просмотр, создание, изменение и удаление пользователей; назначение ролей; metrics.
- **manager:** список пользователей, просмотр пользователя по ID, metrics. Изменять чужие профили и роли нельзя.
- **member:** собственный профиль и базовые функции приложения.
- **Все роли:** изменение собственного имени, email и пароля; работа со своими Items.
- **Items:** сохраняем существующее поведение — admin имеет доступ ко всем, manager и member только к своим.
- **Удаление себя:** сохраняем запрет для admin, разрешаем manager и member.

Согласованные решения: полностью заменить `is_superuser` полем `role`; глобальные настройки не добавлять. URL `/admin` сохранить, пункт меню назвать **Users**.

## Backend и данные

**Один источник истины — `User.role`.**

Добавить строковый enum `Role`: `admin`, `manager`, `member`. Хранить его как строку с `NOT NULL`, default `member` и CHECK-ограничением допустимых значений.

Миграция Alembic:
- Перенести `is_superuser=true` в `admin`, остальных — в `member`; удалить старую колонку.
- При downgrade восстановить boolean: только `admin` становится superuser. Потерю различия manager/member описать в миграции.

В API заменить boolean на `role` в публичной и административных схемах. Администратор может назначать роль при создании и изменении пользователя; неизвестная роль и явно переданный `null` возвращают `422`. Регистрация всегда создаёт member. В схемах signup и `/users/me` запретить дополнительные поля, чтобы попытка передать `role` или `is_superuser` явно отклонялась.

**Проверки доступа — через зависимости FastAPI.**

Добавить `require_roles(*roles)` поверх `CurrentUser` и использовать его для административных операций и чтения пользователей. Проверки владения профилем и Items оставить рядом с загрузкой соответствующего объекта. Отдельные таблицы permissions, middleware и универсальный policy engine не нужны.

Обновить все прежние superuser-проверки, включая служебные email/reset-password endpoints и запрет удаления себя. JWT не менять: роль читается из БД.

Добавить `GET /api/v1/metrics/` для admin и manager: типизированный ответ с фиксированными демонстрационными показателями, явно обозначенными как demo.

Разделить ошибки:
- `401` — отсутствующий, некорректный или истёкший токен, некорректный `sub`, удалённый пользователь; заголовок `WWW-Authenticate: Bearer`.
- `403` — недостаточная роль или неактивная учётная запись.

Bootstrap продолжает использовать существующие `FIRST_SUPERUSER*`, создавая admin. Добавить отдельную идемпотентную dev-команду для manager/member с паролями из окружения; не сбрасывать существующие пароли и роли при повторном запуске.

## Frontend

После изменения схем перегенерировать OpenAPI-клиент; generated-файлы вручную не редактировать.

В одном модуле собрать frontend-правила доступа: просмотр пользователей, управление пользователями, просмотр metrics. Использовать одни и те же правила в навигации, route guards и кнопках; тип роли брать из generated-клиента.

- Общие query options для `currentUser` использовать в `useAuth` и guards через один QueryClient.
- `/admin` открыть admin и manager; manager видит таблицу без Add/Edit/Delete.
- Заменить checkbox superuser на выбор роли в административных формах и отображать роль в таблице.
- Добавить `/metrics` и пункт меню для admin/manager.
- При прямом переходе без прав показывать **Access Denied** с переходом на главную, не запускать запрос защищённых данных.
- При API `403` сохранять сессию и показывать понятную ошибку; при `401` очищать сессию и отправлять на login. Обработать также ошибки из route guards.
- При смене аккаунта очищать Query cache; после изменения пользователей обновлять список и `currentUser`.
- Исправить вкладки настроек: нынешний `slice(0, 3)` ничего не скрывает; admin не должен видеть удаление собственного аккаунта.

## Тесты и критерии готовности

Сохранить текущую структуру тестов. Новые RBAC-проверки собрать в одном модуле с небольшой фабрикой пользователя и заголовков авторизации. Использовать настоящие JWT и БД, без подмены `get_current_user`.

Пять понятных групп, параметризация только внутри одинакового сценария:

1. **Чтение:** список пользователей и metrics разрешены admin/manager, запрещены member.
2. **Управление:** создание, изменение роли и удаление чужого пользователя доступны только admin; при отказе БД не меняется.
3. **Свой профиль:** все роли могут читать и менять свой профиль; передать роль через signup или `/me` нельзя.
4. **Владение:** manager/member не изменяют чужой профиль и Items; admin сохраняет существующий доступ.
5. **Смена роли:** после понижения manager до member тот же JWT больше не открывает metrics.

Существующие login-тесты дополнить проверками `401` и неактивного пользователя; старые проверки boolean заменить проверками роли.

Для новых тестов создавать уникальных пользователей и удалять собственные данные после сценария. Не менять роль общего bootstrap-admin и не строить универсальный тестовый DSL. Запускать на выделенной тестовой БД: существующая session-фикстура удаляет пользователей и Items при завершении.

В Playwright добавить два сценария: manager видит Users/Metrics без управления; member получает Access Denied при прямом переходе и остаётся авторизованным. Существующий admin-сценарий адаптировать к выбору роли. Тестовых manager создавать через административный API, не расширяя открытый `/private` назначением ролей.

Готовность: проверены upgrade/downgrade миграции, backend suite и существующий порог coverage, сборка фронтенда и Playwright. README содержит матрицу прав, краткое объяснение архитектуры, команды запуска, миграций, seed и тестов.
